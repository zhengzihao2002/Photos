# Zero writes to source folders: audit

Promise: Photos never writes, moves, renames, deletes or labels any file in a source folder, and never creates a file beside one. User edits (favourites, titles, captions, keywords, rotation, people corrections) live only in the app database.

_Generated by `node tools/audit-writes.js --write-doc`; the CI job `node tools/audit-writes.js --check` fails when a new write site appears that is not explained in `tools/audit-writes-allow.json`._

## Layers of protection

1. **Static audit** (this table): every call that can change the file system or run a program, with where it writes and why that is safe.
2. **Runtime write guard** (`src/main/write-guard.js`, loaded first in the main process and in every worker thread): wraps Node’s `fs` and `fs/promises` mutating functions and `createWriteStream`. A target that resolves (symbolic links followed, `..` removed, case-folded, Unicode-normalised) inside any registered source folder, or outside the data folder and the temp folders, is refused with an error and a log line. The source list follows the database at once when a folder is added, removed or relinked.
3. **External-tool validation** (`src/main/safe-exec.js`): the only way a program is started. Only `sips`, `ffmpeg`, `ffprobe`, `stat`, `mount` and `plutil` are allowed; every output path must pass the write guard; `sips` must always have `--out`; `ffmpeg` needs `-nostdin`, one input, one output.
4. **Safe deletion** (`src/main/storage/safe-delete.js`): only the contents of a known cache folder inside the data folder can be cleared; symbolic links are removed, never followed.
5. **Read-only disk image test and before/after fingerprint** in CI (`tools/ci-smoke.sh`, `tools/verify-readonly.js`).

## Not visible to the write guard

- SQLite (better-sqlite3) writes library.db, library.db-wal and library.db-shm in the data folder through native code. No SQLite statement attaches another file (no ATTACH, no VACUUM INTO).
- sharp / libvips writes only the file named in `.toFile(...)` (listed above, all inside the data folder) and reads originals read-only.
- onnxruntime reads the model files shipped in the app and the thumbnail JPEGs; it writes nothing (telemetry is disabled with ORT_DISABLE_TELEMETRY).
- Chromium (the renderer) writes to the data folder because Electron’s userData / sessionData / crashDumps / temp paths are redirected there at startup; a few entries that macOS itself files under the bundle id are removed after quit by the residue cleanup.
- Originals are opened only for reading: image-dimensions.js uses open(path, 'r'); sharp, sips, ffmpeg and ffprobe receive the original as input only. `sips` is never run without --out when it changes something, which would edit the original in place.
